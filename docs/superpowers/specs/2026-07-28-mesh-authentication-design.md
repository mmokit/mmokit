# Unit 3 — Mesh authentication and authorization (Design)

**Date:** 2026-07-28
**Status:** Approved

## Goal

Make every mesh channel refuse traffic from processes outside the cluster, encrypt it in transit, and stop the receiving side from believing identity and authority claims made in message bodies — without requiring any configuration for the single-process preset and without a certificate-management story.

## 1. What is broken today, verified at `eb1a34d5`

| Surface | Defect |
| --- | --- |
| Both gRPC servers | No `grpc.Creds`, no interceptor. `host_network.go:148`, `coordinator.go:2219` |
| All three dials | `insecure.NewCredentials()`. `host_network.go:233`, `mesh_control_client.go:195`, `mesh_gateway_client.go:137` |
| `MeshData` | `mesh_data_server.go:24-37` is a bare `Recv` loop into `routeInboundFrame`. No identity check of any kind |
| `MeshControl` | Twelve authoritative sites re-read identity from the message body rather than from the stream that carried it |
| cmdsys RBAC | `callerFromProto` (`cmdsys_transport.go:284-299`) copies `pb.Grants` verbatim into the `cmdsys.Caller` that `InvokeLocal` authorizes against. `Grant{Pattern:"*.*"}` on the wire executes any registered verb |

`rg 'grpc/metadata|UnaryInterceptor|StreamInterceptor|PerRPCCredentials|grpc.Creds'` returns zero hits module-wide. The June 2026 TLS work (`tls_config.go`) is scoped to the client-facing HTTP listeners and closes none of this.

## 2. Threat model

**In scope.** An unauthenticated process that can reach a mesh port. This is the realistic exposure: all four production `NewHostNetwork` callers bind the literal `":0"` (a wildcard ephemeral bind on every interface, `coordinator.go:1838, 2021, 2078, 2112`) and `--control-listen` defaults to `":9100"`, also wildcard. A passive eavesdropper on the network path is also in scope.

**Explicitly not in scope.** A cluster member impersonating another cluster member. See §4.3 — this follows from the shared-secret decision and is not an oversight.

**Documented residual, carried from the umbrella spec.** Peers dial with `InsecureSkipVerify`, so an active on-path MITM can intercept. The answer is network isolation, not PKI. Certificate pinning by fingerprint is declined as out of scope.

## 3. Mechanism

### 3.1 Transport — ephemeral in-memory TLS, lockstep

Both servers get `grpc.Creds(credentials.NewTLS(...))` from a per-process, per-process-lifetime self-signed certificate generated by the existing `generateDevCert()` (`tls_config.go:44`), never written to disk. All three dials get `credentials.NewTLS(&tls.Config{InsecureSkipVerify: true})`.

`generateDevCert` is reused **unchanged**. Its localhost-only SANs and `SerialNumber: big.NewInt(1)` are deliberately irrelevant — `InsecureSkipVerify` means neither is consulted, and "fixing" them would imply a verification that does not happen. `tls_config_test.go:140,155` assert them for the HTTP path.

`Process.httpTLSConfig` is **not** reused. It `sync.Once`-memoizes the client-facing posture and returns nil in the shipped default (`tls_config.go:39` + `bootstrap.go:79-87`); the mesh needs a certificate even when client TLS is plaintext. New `meshTLSOnce` / `meshTLSCert` fields sit beside `tlsOnce`/`tlsConfig`/`tlsSelfSigned` at `coordinator.go:647-649`.

**This is one lockstep commit, and that is free here.** A `grpc.Creds` server cannot accept a plaintext client and a TLS client cannot accept a plaintext server; there is no negotiation or fallback. But every multi-process launch in this repository builds one binary and runs N copies of it (`justfile:82`, `examples/4node-basic/justfile:105`), and every test cluster is N `*Process` values inside one OS process. There is no version-skew path in-repo, so a transition period would be pure liability.

The umbrella spec's "the coordinator generates a self-signed cert" is wrong and is superseded here: every process running a `NewHostNetwork` listener is itself a TLS server for peer dials and needs its own certificate.

### 3.2 Secret transport — stream metadata, not `PerRPCCredentials`

The secret travels in gRPC call metadata attached with `metadata.AppendToOutgoingContext` at the three stream-open sites (`host_network.go:250`, `mesh_control_client.go:212`, `mesh_gateway_client.go:154`). Both services are bidi-stream-only (`mesh.proto:13`, `:404`) and each peer opens exactly one long-lived stream, so this costs zero per-frame bytes.

Server side is a `grpc.ChainStreamInterceptor` on both `grpc.NewServer` option lists. **Stream interceptor only** — a `UnaryInterceptor` would be dead code that a later reader mistakes for coverage.

Comparison is `subtle.ConstantTimeCompare`; a wrong secret and an absent secret both yield `codes.Unauthenticated`.

> **Correction to `docs/roadmap.md:417`.** That bullet says mesh TLS must land after the client-side tasks because "flipping `RequireTransportSecurity()` breaks any dial that has not yet attached credentials." The mechanism is backwards. `RequireTransportSecurity()` is a method on `PerRPCCredentials`, and `grpc@v1.80.0/clientconn.go:494-499` rejects only the combination of insecure transport credentials *with* a per-RPC credential demanding security. A dial with no per-RPC credentials has an empty slice and the loop never runs. Using metadata rather than `PerRPCCredentials` removes the concern entirely. The same bullet says "both client-side tasks"; there are **three** production dials, and the one it drops is `ConnectPeer` — the payload plane.

### 3.3 Metadata key

One lowercase ASCII key, `mmokit-cluster-secret`. No `-bin` suffix: that suffix forces base64 encoding. gRPC lowercases metadata keys, so the constant must already be lowercase or the server lookup silently misses.

### 3.4 Configuration model

`universe.Config.ClusterSecret string`, which appears on `mmokit.Config` automatically — `pkg/mmokit/mmokit.go:254` declares `type Config = universe.Config`, a pure alias with no forwarding code.

Precedence is flag > env > preset field, achieved without `flag.Visit` (used nowhere in the module): `BindFlags` reads `MMO_CLUSTER_SECRET` into the field *before* calling `stringFlag`, so the env value becomes the flag's default and an explicit flag beats it. This would be the module's first engine-level env var; the only existing `os.Getenv` calls are `POSTGRES_URL` (`cmd/server/main.go:126`, game-level) and `BOT_DEBUG`.

The env read is **repeated as a zero-value fallback inside `New()`**, next to the `WireLimits.Normalized()` line at `coordinator.go:810` whose in-source comment states the reason: *"flag defaults never reach a Config built by a test fixture."* `New`'s `if !flag.Parsed()` guard (`coordinator.go:764-768`) is always false under `go test`, so `BindFlags` never runs there. This was verified empirically, not merely read: a probe test in `pkg/universe` prints `flag.Parsed()=true`, `ControlListen=""`, `HTTPPort=8080` — the port arriving from `New`'s fallback, not the flag. A corollary the roadmap does not state: `BindFlags` is also skipped for any game that calls `flag.Parse()` itself, so an env read placed only in `BindFlags` is invisible on **two** live paths.

`Config.ClusterSecret` carries a doc comment forbidding it from any dump path. `Process.Config()` (`coordinator.go:1361`) hands out a mutable `*Config`.

### 3.5 Zero-config posture — role-gated, resolving the criterion 6/7 conflict

Criteria 6 and 7 as written conflict. If auto-generation fires whenever the secret is empty, `just distributed-space` runs five separate OS processes, each calls `crypto/rand` independently, every `RegisterHost` mismatches, and the cluster never forms — which is not "continues."

A process-global `sync.Once` does not fix this. It repairs in-process test clusters (all `*Process` in one binary) and breaks every real multi-process deployment for exactly the reason above.

**Resolution: gate on the role set**, reusing the discriminator already in source at `coordinator.go:1760-1761`.

```
selfContained := roles.Has(RoleCoordinator) && roles.Has(RoleHost)
```

| Condition | Posture |
| --- | --- |
| `ClusterSecret != ""` | Enforce (criteria 2, 3, 4) |
| `ClusterSecret == ""` and `selfContained` | Generate `crypto/rand`, enforce, log fingerprint once (criterion 6) |
| `ClusterSecret == ""` and not `selfContained` | Leave empty, warn once, accept unauthenticated peers, dial without metadata (criterion 7) |

Enforcement is therefore always `if serverSecret != ""` — provenance-gated, never a global flip. There is no single instant at which plaintext-authentication stops being accepted, which is what makes fixture propagation far less load-bearing than `docs/roadmap.md:417` claims.

`selfContained` is sound because an `all`-preset process can never dial out: `Config.IsRemoteHost` requires `len(roles)==1 && roles.Has(RoleHost)` (`coordinator.go:406-408`) and `isStandaloneGateway` requires `!roles.Has(RoleCoordinator)` (`coordinator.go:2001-2003`). A cluster control plane is spelled `coordinator` or `coordinator,gateway`, never `all`.

**Not** gated on a loopback check: `isLoopbackBind` returns false for an empty host (`tls_config.go:75-76`, whose own doc comment says so), so the heuristic never fires for `":9100"`. **Not** gated on `CoordinatorAddr == ""` either: the distributed coordinator (`justfile:117`) has none.

Placement is in `Build()` between `c.roles = roles` (`:1606`) and `startControlPlane()` (`:1762`), and after the log-category enable at `:1715-1718` — `Logger.Log` early-returns on a disabled category. It cannot live in `New()`; `ParseRoles` runs once, at `:1602`. `Build()` works on the local copy `cfg := c.cfg` and must write back with `c.cfg = cfg`.

The fingerprint is `sha256(secret)[:4]` hex — the pattern at `pkg/services/auth/token.go:26` — and **never** the value. Remote hosts install a MeshControl log forwarder (`coordinator.go:2044-2046`) that ships every enabled log line over the very channel being secured.

Both the fingerprint line and the criterion-7 warning are once-per-process behind a `sync.Once` on `Process`. `CatMeshCell` is force-enabled via `StartupCategories` (`stage.go:49`), and 37+ test functions reach `newDistributedFixture`; without the guard `go test ./pkg/universe` gains roughly 100 warning lines.

The fingerprint must go through `c.Log.Log` (→ `log.Printf` → stderr), never `fmt.Println`. `just client-sdk` / `space-sdk` / `csharp-sdk` pipe server **stdout** into `cmd/sdkgen` (`bootstrap.go:198`).

## 4. Authorization

Authentication answers "is this peer in the cluster." Authorization answers "is this peer allowed to do *this*, as *itself*." A phase that stops at secret-plus-TLS ships a cluster in which every authenticated peer is an unrestricted `*.*` cluster admin.

### 4.1 Control-plane identity — bind to the stream

All twelve body-identity reads use the stream-bound ID; a mismatch is logged and dropped, never silently rewritten. `mesh_control_server.go:174` already captures `hostID := reg.HostId` at registration, so the value exists — it is simply not consulted downstream.

### 4.2 Registration admission (criterion 9, re-scoped)

The criterion as written — "cannot evict a live peer **or overwrite its `GrpcAddr`**" — is half wrong. `GrpcAddr` refresh is **mandatory**: all four production `NewHostNetwork` calls bind `":0"` and the advertised value is the live listener (`mesh_control_client.go:239-244`), so freezing it makes a restarted host permanently unreachable on the payload plane while its control stream looks healthy. `State: RemoteHostRegistered` is likewise the only exit from `RemoteHostDead` (`Touch` has no `Dead→Live` arm; `Remove` is graceful-only), so the full field refresh must survive.

Re-scoped:

> **9.** A `RegisterHost`/`RegisterGateway` for an ID **still being defended** by an incumbent peer is rejected with `codes.AlreadyExists` and leaves the registry untouched. Admission is unchanged in every other case, and an admitted registration performs the **full** field refresh — `GrpcAddr`, `State`, `OwnedCells`/`Sessions`, `LastHeartbeat` — because crash-reconnect depends on all four.

"Still defended" is three terms, and each closes a verified scenario that a simpler predicate breaks:

| Term | Scenario it closes |
| --- | --- |
| `!killClosed(cs)` — non-blocking select on the incumbent's kill channel | `host.kill` (`builtins_host.go:113-134`) closes `kill` via `cancelStream` but the map delete happens later in the handler's `defer` (`:239`). The host redials after 200 ms. Both stream-presence and pure-staleness predicates reject it, turning a documented ~3 s reassignment into a lockout |
| `!h.Local`, unconditional and first | `checkLiveness` skips `Local` entries *before* the staleness test (`coord_assignment.go:111-115`) and `Touch` is unreachable without a control stream, so a local host's `LastHeartbeat` is frozen at `RegisterLocal` time and stale forever. A staleness-only rule **hands over** the well-known IDs `"local"` and `"inproc"` |
| `State != RemoteHostDead` **combined with** `time.Since(LastHeartbeat) <= deadThreshold` | Dead is sufficient but not necessary. `checkLiveness` requires `State == RemoteHostLive` before testing staleness (`:108-110`), so a host that registers and never heartbeats stays `Registered` forever and is never marked Dead; only the staleness term admits it |

Plus a cross-map term: `sendCoordMessageToHost` falls back to `gatewayStreams[hostID]` (`:1035-1047`) on an unenforced assumption that host and gateway IDs never collide, so each guard must consult both maps.

Liveness is **application-level heartbeat freshness**, never transport liveness. Heartbeat 1 s (`mesh_control_client.go:341`), `deadThreshold` 3 s / `gatewayDeadThreshold` 5 s (`coord_assignment.go:73,78`), watcher tick 500 ms. Server keepalive is 60 s/20 s — a ~80 s bound, 25× the registry threshold, and unusable as a signal. **Residual:** a genuine abrupt-loss restart inside the first 3 s is rejected once and retried by the client's 200 ms-floor backoff. Bounded and self-healing; state it rather than pretending the window is zero.

Network-partition heal is **not** a re-registration scenario. `runConnection` returns only on a recv error and the client keepalive is also 60 s/20 s, so a partition shorter than that attempts no reconnect at all. The real partition hazard is a zombie, below.

**Two fixes must land with the guard or it is a net regression:**

1. **Close the zombie.** Re-registration is the sole exit from `RemoteHostDead`, and a partition-healed host never re-registers. A host marked Dead at 3 s whose stream then recovers heartbeats forever with `State` stuck at Dead, excluded from `reassignOrphanedCells`' `liveIDs`. Fix: when `checkLiveness` marks a host Dead, also `cancelStream` it. That converts the zombie into a clean reconnect and makes the guard's stream term honest.
2. **Give the gateway side a `cancelStream`.** `:981-990` consults only `s.streams`. Without a gateway variant there is no operator escape hatch for a wedged gateway ID — and a locked-out gateway breaks client reconnect outright (§4.5).

The criterion's real motivation, which should be stated: today eviction is unconditional, so two processes sharing a `--host-id` flap forever, each evicting the other every 200 ms.

### 4.3 Payload-plane binding (criterion 12, re-scoped) — reject `MeshFrame.sender_id`

**`docs/roadmap.md:225` prescribes a `sender_id` field on `MeshFrame`. That is the wrong mechanism, and the paragraph is internally contradictory.** It says both "populate `sender_id` server-side from the authenticated stream" and "if per-frame width is the concern the answer is an interned numeric peer ID." proto3 strings have implicit presence, so a field the sender never sets is never serialized:

- **Server-populated** → zero wire bytes, zero information carried from sender to receiver. It is written by the server and read by the server. That is a function parameter with a lockstep redeploy attached, and the "interned numeric ID" fallback argues about the width of a field never on the wire.
- **Sender-populated** → attacker-controlled, so the server must unconditionally overwrite it, and the wire bytes are waste.

Server-side population also requires mutating a gRPC-owned received message, which `host_network.go:955-958` explicitly prohibits: *"Construct a new PlayerAssignment rather than mutating the gRPC-owned inbound proto. The gRPC runtime may retain the original buffer."* And it introduces a **verified data race**: `service_event_dispatch.go:53-62` builds one frame and `:64-68` fans it to N peers, each of whose `runPeerSender` calls `p.stream.Send(of.frame)` — stamping a field in the send path is a concurrent write against in-flight marshaling, a guaranteed `-race` failure in the nightly job.

**Mechanism: a peer ID captured once at stream open, threaded as a parameter.**

```go
func (n *HostNetwork) routeInboundFrame(senderID string, frame *meshpb.MeshFrame) (err error)
```

Sixteen call sites, all in `pkg/universe`, all compiler-checked. Three are production:

| Site | Value |
| --- | --- |
| `mesh_data_server.go:33` | captured once **before** the `for` loop from `metadata.FromIncomingContext(stream.Context())` — the same context Phase A already reads for the secret, so the capture point is free. `MeshData_DataServer` embeds `grpc.ServerStream`, so no interceptor is needed to reach it |
| `host_network.go:327` (`runPeerReceiver`) | `p.hostID`, already in scope from the dial |
| `grpc_bridge.go:102` (always-proxy self-route) | `b.host.ID` |

That third site is the decisive argument for a parameter over a field. It bypasses gRPC entirely and is production-reachable — `--gateway-mode` is a real flag (`bootstrap.go:116-118`) with values `local-shortcut|always-proxy`. A parameter makes the compiler demand a value there; a proto field silently yields `""`, and "empty" then has to be either a silent drop (breaks a feature) or a silent bypass (reopens the hole). There are ten `&meshpb.MeshFrame{` producer sites — ten chances to forget, with no compiler help.

**Per-arm rules, not a blanket check.** `docs/roadmap.md:227` asserts *"There is no legitimate case where a frame's claimed identity differs from its stream sender."* That is false, three times over, and a blanket rule drops the hottest arm in the mesh:

| Arm | Rule | Why |
| --- | --- | --- |
| `ClientInput.GatewayId` | `== senderID` | both producers stamp their own ID (`gateway.go:1161`, `:1185`) |
| `ClientDisconnect.GatewayId` | `== senderID` | `gateway.go:520` |
| `PlayerAssignment.GatewayId` | `== senderID` | `gateway.go:963` |
| `ServiceEvent.SourceProcessId` | `== senderID` | `service_event_dispatch.go:56` |
| `ClientFrame.GatewayId` | `== n.hostID` — the **receiver's own** ID | producers are hosts and the field names the *receiving* gateway (`virtual_conn_manager.go:298-308`, `:657-666`). One frame per player per tick at `TickRate = 20`; a sender check drops 100% of replication traffic. This is the currently-missing untracked-path check — `gateway.go:754` already enforces it for `tracked` |
| receipt marker host | `== n.hostID` | already checked at `host_network.go:769`; keep |
| `ForwardInput.GatewayId` | **no sender check possible** | legitimately names a third-party gateway on a host→host frame (`grpc_bridge.go:294-308`). A blanket rule breaks cross-host input forwarding during the handoff grace window |
| `CellTransferReady.HostId` | `== senderID`, or delete the arm | zero production producers; the only construction repo-wide is a test |
| `CellTransferAbort` | delete the arm | zero constructions anywhere |
| `FromCellId` / `SourceCellId` | **do not check** | requires cell→host resolution through the eventually-consistent `cellToHost` snapshot, stale by construction during commit windows |

`docs/roadmap.md:227` also claims `newReplicationReceiptFrame` "populate[s] `GatewayId` with the sending process's ID." It does not — `replication_receipt.go:85` **echoes** `cf.GatewayId` from the inbound frame. Self-equality is enforced upstream by `gateway.go:754`, not by the producer.

**Criterion 12 must be re-scoped, because as written it is unachievable.** The locked design is *one secret shared by every peer*. `MeshData` has no registration handshake, `n.peers` is the outbound dialed map with no association to inbound server streams, and TLS is server-side only with no client certificates — so `peer.FromContext` yields no identity. Whatever peer ID a stream claims, in metadata *or* in a proto field, is asserted by the sender and authenticated only as "holds the cluster secret."

> **12.** `MeshData` frame contents are bound to a peer identity captured once at stream open and constant for the stream's lifetime. Payload-carried process IDs are verified per-arm against it; a mismatch is logged and dropped, never rewritten. **Residual, deliberately accepted:** the cluster secret is shared, so this excludes outsiders and enforces per-stream identity consistency — it does not prevent one authenticated cluster member from claiming another's ID. Insider peer impersonation requires a per-peer credential and is out of scope for this phase.

What stream binding does buy is real: outsider exclusion, and the death of the "one stream, many identities" attack. Say so, or unit 14 is recorded Done while insider impersonation is untouched.

**Testing trap.** Criteria 3 and 12 **cannot** be tested against the `all` preset. `coordinator.go:1870-1979` never assigns `h.Network`, so `newBridgeForCell` returns a plain `*cellBridge` and `routeInboundFrame` is structurally unreachable. Any acceptance test written against `all` is a false pass. Use `newDistributedFixture` or a raw `NewHostNetwork` pair.

### 4.4 RBAC (criterion 10, re-scoped) — delete grants from the wire

Criterion 10's remedy, "authority is resolved locally," is **not implementable as written**. The store inventory on a host is empty:

- `d.grants` is `NewInMemoryGrantStore()` by default (`dispatcher.go:60-61`) because `coordinator.go:909-915` passes no `Grants:` field, and `InMemoryGrantStore.Set` has zero non-test callers.
- Worse, `InvokeLocal` — the only entry point mesh traffic reaches — **never reads `d.grants` at all**. Its sole gate is `Check(caller, cmd.Capability)` against the wire-supplied grants. Only `Invoke` merges the store, and that runs on the *originating* process.

And a lookup keyed on `Caller.ID` would be a **privilege escalation, not a restriction**. `admin_accessors.go:374-378` synthesizes `Caller{ID:"admin", Grants:[{"perf",true}]}` for `perf.snapshot`; `pkg/admin/admin.go:246-250` seeds an operator literally named `admin` with `["*.*"]`. Discarding the narrow wire grant and looking `"admin"` up in `engine.admin_operators` widens that identity from one capability to every capability on every host. It also cannot resolve `"console"`, `"admin:bots-publisher"`, `"test-op"` or `"test-perf"` — three of the four production callers are synthesized in Go and are rows in no table — has no replication or invalidation transport, and would make Postgres a framework requirement on every host.

A coordinator-signed capability token is redundant: the host's `CommandRequest` arrives on the stream *the host itself dialed* to `cfg.CoordinatorAddr`, so once Phase A authenticates that channel, "this came from the coordinator" is structurally proven. A token minted with the same shared secret proves the same proposition, needs new HMAC code (`crypto/hmac` has zero occurrences module-wide), and drags a proto change into Phase B for no security delta. There is no delegation to protect — `meshControlTransport.Send` is the only producer of `CoordMessage_CommandRequest` and errors when `controlServer == nil`, assigned only inside `startControlPlane` under the coordinator-role gate.

> **10 (revised).** RBAC grants are removed from the mesh wire format. On a mesh receive path, authorization is the authenticated peer relation — a process accepts a `CommandRequest` only from an authenticated coordinator, and executes it because the coordinator already authorized it against its own operator store. `Caller.ID` and `Caller.Source` are carried for audit only and are never inputs to an authorization decision.

This extends a precedent already inside the same function: `executeCommandRequest` **already** overwrites one wire-supplied identity field from the transport — `caller.Source = cmdsys.SourceMeshControl` at `cmdsys_transport.go:339`, commented *"arriving via MeshControl means it's a MeshControl caller regardless of what the sender claims."* Extending that from `Source` to `Grants` is the same move.

The RBAC decision does not disappear; it stays where the store is. `Invoke` on the coordinator already runs `Check` against DB-sourced operator grants *before* resolving targets and sending. The host was never adding security — it re-ran the same check against grants the coordinator had just serialized.

Two things the criterion presupposes that do not exist, and must be built:

- **"Caller.ID is preserved for audit"** — there is nowhere to preserve it to. `InvokeLocal` emits no audit record, and the production sink is `cmdsys.NoopAuditSink{}` (`coordinator.go:913`). `pkg/admin`'s ring is fed only by HTTP handlers. A mesh-delivered command leaves zero trace today.
- **Route is never checked.** `InvokeLocal` goes Lookup → Check → Handler without consulting `cmd.Route`. On the coordinator's inbound-from-peer paths that reaches `admin.operator.create` — `RouteLocal`, and it defaults grants to `["*.*"]` when the argument is empty. That escalation is coordinator-only, and it lives behind two handlers with **zero legitimate producers**: `meshpb.HostMessage_CommandRequest` is constructed nowhere in the module. Deleting those two receive paths closes it more completely than any route check.

### 4.5 Two invariants the guard can violate

Both are recorded in project memory and both are reachable from criterion 9:

- **A locked-out host keeps running its cells.** Nothing in `runConnectLoop` tears cells down on a registration error; it backs off. Meanwhile every boundary handoff — *including same-host ones* — notifies the real coordinator over MeshControl (`grpc_bridge.go:211`), because `b.coord` on a host is a local stub. So a rejected host re-registration silently breaks routing for every player crossing a cell boundary on that host.
- **A locked-out gateway breaks client reconnect outright.** `resolveSpawn` takes the `g.controlClient` branch when `g.coord == nil` (`spawn_resolver.go:81-105`) with a 2 s deadline and, on failure, falls through to `defaultSpawnLocation()` returning `IsReconnect=false`. Every reconnecting player becomes a fresh spawn at the centre of cell (0,0) with `applyResolveSpawnReconnect` never running — the duplicate-entity / clone-and-loot failure class, produced by the security fix.

Both need distributed-fixture regression tests, named in Phase B.

## 5. Bundled schema change — the replication-receipt oneof arm

`newReplicationReceiptFrame` encodes a host ID and a token into `DestCellId` via `replicationReceiptMarker(sourceHostID, token)` — a cell-ID string field carrying neither a cell nor an ID — and rides a `^uint32(0)` channel sentinel. That workaround exists because a proto change felt expensive. It is fixed here, and this is the **only** proto change in CE-006.

The overload is two-directional; land both legs or half survives:

- outbound tracked leg: add `source_host_id` + `receipt_token` to `ClientFrame`, replacing `virtual_conn_manager.go:299`
- return leg: a new `ReplicationReceipt` message and `MeshFrame` oneof arm, replacing `replication_receipt.go:82/88/89`

Then delete `replicationReceiptNamespacePrefix`, `replicationReceiptMarkerPrefix`, `replicationReceiptChannel` and the four parse helpers.

Separately, Phase B deletes `repeated Grant grants = 3` from `message Caller` and the `message Grant` definition. `id = 1` / `source = 2` survive contiguously, so the repo's renumber-on-removal rule is satisfied with no renumbering.

Both proto edits require `just proto` **and** `just fuzz-corpus` in the same commit. `TestFuzzSeedCorpus` runs under the required CI `go test` job, not the nightly.

## 6. Out of scope

- CA-based mTLS, a CSR-signing bootstrap, or any certificate management. Explicitly rejected by the locked decision; the two surviving `TODO(mTLS)`/`TODO(S4)` comments name a mechanism that decision rejected and are **deleted, not implemented**.
- Certificate pinning by fingerprint.
- Per-peer credentials, and therefore insider peer impersonation (§4.3).
- Defending against an active on-path MITM.
- Coordinator-console chat moderation over the wire, which is **already broken** at HEAD: chat verbs are `RouteService`, `executeCommandRequest` forces `SourceMeshControl`, so `operatorOpContext`'s `uuid.Parse("console")` fails and the `SourceConsole → SystemTrusted` bypass no longer applies. Pre-existing, live in `examples/4node-basic/justfile:128-129`, and must **not** be "fixed" by preserving `Source` — that reopens a trust bypass.

## 7. Verification

Per-criterion tests are enumerated in the plan. The load-bearing ones:

- `RegisterHost` without the secret → `codes.Unauthenticated`, and `hostRegistry.Get` stays nil.
- A `MeshData` stream without the secret → rejected, and no frame reaches `routeInboundFrame`.
