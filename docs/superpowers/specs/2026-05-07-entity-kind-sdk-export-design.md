# Entity-Kind SDK Export and Proto Pipeline Retirement

**Status:** Landed 2026-05-07
**Author:** brainstormed via session
**Supersedes parts of:** none — incremental cleanup on top of the 2026-05-06 events/operations channel redesign

## Goal

Eliminate the last client-facing protobuf type (`gamepb.EntityType`) by teaching sdkgen to emit a TypeScript const block from the existing entity-kind registry, and retire the now-empty proto pipeline that supported it (`proto/gamepb/`, the C# emitter, `gen/csharp/`, `gen/es/`).

After this lands, **the only remaining proto in the codebase is `proto/meshpb/`**, which is server-internal mesh data plane only. Game devs writing against this framework declare typed events, operations, components, and entity kinds in plain Go — and get a self-contained TypeScript SDK out of the same schema dump that already powers everything else.

## Background

`gamepb.EntityType` is a proto-generated enum (Ship/Asteroid/Projectile/Station/LootCrate/NPC) used in three places:

1. **Server-side Go**: `internal/component/components.go:17-21` derives `TypeShip = uint8(gamepb.EntityType_ENTITY_TYPE_SHIP)` etc. Spawn helpers, AI logic, and replication tag entities with these `uint8` constants.
2. **Bot AI**: `internal/bot/bot.go:363,386` checks `e.Type == gamepb.EntityType_ENTITY_TYPE_ASTEROID` / `_STATION` for target selection.
3. **Web client**: `web-pixi/src/constants.ts:1` imports `EntityType` from `@gen/game_pb.js` for color-table keys.

This was the last cross-language enum keeping `proto/gamepb/` alive. The 2026-05-06 spec (Plans 1–3) retired the rest of the client-facing protobuf surface; the 2026-05-07 "Bucket A" cleanup deleted `proto/enginepb/` and `proto/basicpb/` outright. `gamepb` survived only because TS needed `EntityType`.

The key insight: **`mmokit.RegisterKind[T](p, kindID, name, ...)` already encodes `(numericID, name)` pairs for every entity type.** The schema dump's `entities[]` array — already consumed by sdkgen for entity-class generation — carries `kind` (uint8) and `name` (string) fields. The proto enum was a redundant parallel registry.

So the migration needs no new mmokit API. The kind registry IS the enum source of truth. sdkgen learns to emit one extra TS file from data it already has.

Unity (gen/csharp) is unused — confirmed during brainstorming. The C# emitter and gen/csharp output are dead weight and ride along in this cleanup.

## Design

### Three workstreams

**Workstream 1 — Native Go consts in `internal/component`.**

Replace the proto-derived constants with plain `uint8` consts and rename to match the framework's `Kind*` convention (used throughout CLAUDE.md and the public `RegisterKind` API). The proto enum currently assigns `_SHIP=0`, `_ASTEROID=1`, `_PROJECTILE=2`, `_STATION=3`, `_LOOT_CRATE=4`, `_NPC=5`. The web client regenerates its SDK in lockstep with the server, so wire values are not preserved across this change — compact to consecutive integers and drop the unused `_PROJECTILE` slot:

```go
// internal/component/components.go
const (
    KindShip      uint8 = iota  // was TypeShip      (proto _SHIP=0)
    KindAsteroid                // was TypeAsteroid  (proto _ASTEROID=1)
    KindStation                 // was TypeStation   (proto _STATION=3 → 2)
    KindLootCrate               // was TypeLootCrate (proto _LOOT_CRATE=4 → 3)
    KindNPC                     // was TypeNPC       (proto _NPC=5 → 4)
)
```

**Projectile dead code**: the proto enum has `_PROJECTILE = 2`, and `web-pixi/src/constants.ts:12` has a `[EntityType.PROJECTILE]: 0xffff44` color entry. But no `RegisterKind` registers a Projectile kind anywhere — the value is referenced only in stale `internal/component/README.md` docs. The migration drops the projectile color entry from `web-pixi/src/constants.ts` and refreshes the README. The byte slot is reclaimed, not reserved.

`internal/component/components.go` drops the `gamepb` import. Every callsite of `gamecomp.TypeShip` / etc. across `internal/game/`, `internal/bot/`, `cmd/botclient/` is updated to `gamecomp.KindShip` / etc. Bot AI's `gamepb.EntityType_ENTITY_TYPE_ASTEROID` checks become `gamecomp.KindAsteroid`.

Bundle types (`ShipBundle`, `AsteroidBundle`, etc.) keep their existing names — only the constants are renamed.

**Workstream 2 — sdkgen TS emitter.**

The schema dump's `entities[]` array already contains `{kind: uint8, name: string, bindings: [...]}`. sdkgen already iterates it to generate per-kind classes (`Ship`, `Asteroid`). Add one new emitter that consumes the same array and writes a TS const file:

```typescript
// <sdk>/entityType.ts
// Generated by sdkgen — do not edit.
//
// Mirrors the entity-kind registry from RegisterKind[T](p, kindID, name, ...).
// Wire values are stable across server restarts; reordering breaks clients.

export const EntityType = {
    Ship: 0,
    Asteroid: 1,
    Station: 2,
    LootCrate: 3,
    NPC: 4,
} as const;

export type EntityTypeValue = typeof EntityType[keyof typeof EntityType];
```

`as const` chosen over `enum` for tree-shakeability, no runtime overhead, and no reverse-mappings (consumers only forward-lookup).

The kind names come straight from the second arg of `RegisterKind` — currently `"Ship"`, `"Asteroid"`, etc. Casing follows whatever the game declares; the implementation does no transformation. (Today's TS consumers use `EntityType.SHIP`; after migration they use `EntityType.Ship` — sites updated as part of this change.)

The new emitter is a small addition to `cmd/sdkgen/`, mirroring the existing `broadcasts.go` / `inputs.go` / `operations.go` shape. Output file name and the SDK `index.ts` re-export line are added in the same generator.

**Workstream 3 — Delete the proto pipeline.**

After workstreams 1+2 land, no Go or TS code references `proto/gamepb/`, `gen/go/gamepb/`, `gen/es/gamepb/`, `gen/csharp/`, or the C# emitter. Delete:

- `proto/gamepb/game.proto` (just the `EntityType` enum, the only thing left there)
- `gen/go/gamepb/` and `gen/es/gamepb/` directories (gitignored, but cleaned for tidiness; `just proto` won't regenerate them after the proto file is gone)
- `gen/csharp/` directory and the `protocolbuffers/csharp` plugin entry in `buf.gen.yaml`
- `gen/es/` directory and the `bufbuild/es` plugin entry in `buf.gen.yaml` (no remaining TS imports of `@gen/...` after web-pixi switches to the SDK; mesh is server-only)
- Vite + tsconfig path alias entries for `@gen/game_pb.js` in `web-pixi/vite.config.ts` and `web-pixi/tsconfig.json` (the last live alias)
- Unity references in `CLAUDE.md` and `README.md` (the "Unity client (Engine.cs + Game.cs)" line and the proto codegen section's `gen/csharp/` bullet)

After: `proto/` contains only `meshpb/`. `buf.gen.yaml` keeps only the two Go plugins (`protocolbuffers/go` + `grpc/go`) targeting `gen/go/meshpb/`.

## Acceptance criteria

- `proto/` directory contains only `meshpb/`
- `gen/csharp/` and `gen/es/` directories do not exist after `just proto`
- `buf.gen.yaml` has only Go plugins
- `grep -rn "gamepb\|@gen/game_pb\|@gen/" --include="*.go" --include="*.ts"` (excluding `gen/`, `docs/`) returns zero hits
- `grep -rn "gamecomp\.Type\(Ship\|Asteroid\|Station\|LootCrate\|NPC\)" --include="*.go"` returns zero hits (all renamed to `Kind*`)
- web-pixi imports `EntityType` from the generated SDK, not `@gen/...`
- `<sdk>/entityType.ts` exists and exports the const block matching the wire values
- `go vet ./...` and `go test ./...` clean
- Both TS typechecks (`web-pixi`, `examples/4node-basic/web`) clean
- `just proto` succeeds and produces only `gen/go/meshpb/`
- Server and freshly-regenerated SDK agree on byte values (a stale client built before this change sees different bytes for Station/LootCrate/NPC and would mis-color those — that's expected; clients regenerate the SDK as part of this change)

## Out of scope

- Multi-game support for the sdkgen emitter (the kinds emitted are whatever the dumping binary registers; that's already how sdkgen works for everything else)
- A "stringer"-style kind name lookup at runtime in Go (the existing `EntityKindDefs` already exposes name + kind ID; no new API needed)
- Reordering wire values further (e.g. alphabetical) — kept in declaration order minus the projectile gap
- Renaming `kind` to `type` (or vice versa) in the schema JSON — keep the existing field name so the SDK template change is purely additive
- Deleting `proto/meshpb/` — that's the gRPC mesh data plane; out of scope for client-facing cleanup
- Adding any other Go-native enum to the SDK — only `EntityType` is migrating in this round; if a second cross-language enum appears later, the same emitter generalizes (rename `entityType.ts` to a multi-export shape at that point)

## Risks

- **Iota ordering.** If the plan task uses a different declaration order than the existing usage assumes, the wrong byte ends up on the wire (e.g. spawning a Ship sends a 1 and the SDK colors it asteroid-brown). Mitigation: the iota block matches the proto enum's existing ordering minus Projectile (Ship → Asteroid → Station → LootCrate → NPC); kind values appear only in `RegisterKind` calls and the few `gamecomp.Kind*` references, all updated in a single commit, all caught by Go static checks.
- **Bot decode.** The bot's pre-auto-replicator world.go layouts (flagged as pre-existing tech debt in Plan 3 Phase 4) consume the `Type` byte as `uint8`. Renaming `gamepb.EntityType` → `uint8` should be a no-op in the snapshot decoder, but the pre-existing decode failures may obscure regressions during smoke testing. Mitigation: rely on Go-side static checks + bot unit tests, not live smoke.
- **Unity user.** If Unity isn't actually unused (despite confirmation), deleting `gen/csharp/` breaks them. Mitigation: the user has confirmed Unity is unused. Documentation and `buf.gen.yaml` deletion is reversible from `git revert`.
- **TS casing change.** `EntityType.SHIP` → `EntityType.Ship` is a hard break; consumers must update in lockstep. Mitigation: only one TS consumer file (`web-pixi/src/constants.ts`), 5 sites; both sides land in the same commit.

## Validation

After implementation:

1. `go vet ./...`, `go test ./...` clean
2. `just proto` produces only `gen/go/meshpb/`
3. `bunx tsc --noEmit` clean in both `web-pixi/` and `examples/4node-basic/web/`
4. `just dev` smoke: connect via web-pixi, observe correct entity colors (ships blue, asteroids brown, etc.) — confirms server byte values match the regenerated SDK end-to-end
5. Static greps in the acceptance criteria all pass
